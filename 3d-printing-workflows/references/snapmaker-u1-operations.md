# Snapmaker U1 operations (optional vendor-specific reference)

Vendor, firmware and slicer specifics from sessions on stock firmware 1.5.x and the community "Extended" firmware (paxx12). Everything here is version-dependent: re-read the live printer, the matching firmware documentation and the current release notes before acting. Use `<printer-host>` for the operator's configured printer; never record real addresses or credentials. General control rules are in `printer-control-and-safety.md` and apply first.

## 1. Identity and channel naming

- Positively identify the printer through Moonraker: server info with `klippy_connected=true` and `klippy_state=ready`; `GET /machine/system_info` with `product_info.machine_type` of the expected model, plus firmware and active interface.
- User-facing heads are **E1 to E4**; Klipper uses zero-based names. `e0` or `extruder` is E1, `e1` or `extruder1` is E2, `e2` is E3, `e3` is E4. `filament_detect.info` entries follow the same zero-based order (`info[3]` is E4). State both names in any result and never report internal `e3` as physical E3.
- For a job started through the touchscreen or Fluidd, do not infer the physical tool from raw slicer `T0` to `T3`: the start UI can remap logical filament indexes to loaded physical heads. Read the logged `SDCARD_PRINT_FILE_WITH_PARAMETERS ... MAP_TABLE` (for example `[[0, 3]]` sends logical filament 0 to E4).

## 2. Extended firmware: remote screen and access toggles

- Verify an Extended install through the firmware-config API status (touchscreen "Firmware Version" usually shows only the base version). Enable the vendor's advanced mode, restart while idle, then require an Extended profile and build plus `klippy_state=ready` before changing features.
- Treat every firmware-config toggle as a service-restarting mutation: idle check, one setting at a time through the documented settings endpoint, re-read settings, test the real service, and require ready afterwards.
- **Remote screen** (touch injection) is control, not monitoring. Use the firmware's native authenticated route (`/screen/`), not another VNC stack. Enable it only through the firmware-config control surface, not by hand-editing include files. Screen capture proves only framebuffer access; touch also needs access to the input device, normally through the root-managed init service. Before reporting touch control as working, inspect the actual server process identity (UID) and the input-device permission and privilege boundary from the installed firmware's documentation, not a framebuffer GET alone; until that identity/permission evidence and any required, explicitly authorised functional check are complete, report framebuffer-only access and touch as UNVERIFIED; this reference tests nothing on a live printer. Verify the local service, the HTML route, the proxied route over the protected origin, and a GET of the snapshot returning `image/png` with a non-empty payload. Keep the printer's reverse proxy inside the existing private network and TLS boundary.
- **Both** remote-screen controls must be effective, and the firmware-config control surface is how they are set, not hand-editing (reference names are firmware-version-specific: read them back from the installed firmware's documentation and settings, never invent API payloads). Relative to the printer config root: `extended/extended2.cfg` with `[web]` `remote_screen: true` (framebuffer back end), and `extended/moonraker/04_remote_screen.cfg` with `[webcam gui]` `enabled: true`, `service: iframe`, `stream_url: /screen/`, `snapshot_url: /screen/snapshot`, `aspect_ratio: 480:320` (front end). If `S99fb-http` is referenced, it is the native local framebuffer service on loopback port 8092 behind the protected `/screen/` route: leave it idle until explicitly authorised for control, and add no new VNC stack and no WAN exposure. This reference activates nothing.
- **Optional LAN-only SSH and RTSP:** only with explicit authorisation; see `printer-control-and-safety.md` section 3. RTSP requires the internal camera set to the Extended-supported provider and an `OPTIONS` plus `DESCRIBE` success.
- Keep AFC Lite disabled unless BOTH a compatible external automatic filament changer exists AND a deliberate Fluidd/Mainsail setup is made; it is not a prerequisite for native multi-toolhead changes, OpenRFID, SpoolLink or Spoolman.
- After a local Extended flash, a Spoolman browser integration needs the Spoolman service's allowed CORS origin set to the printer's actual current browser origin (never wildcard; recreate only that service; prove a permitted origin gets `Access-Control-Allow-Origin` on `GET` and `OPTIONS` and an unrelated origin does not; update it if the printer moves between Wi-Fi and Ethernet).
- Do not recommend an Extended release merely because it is newer than the factory firmware: compare with the **currently installed** stock version and check the feature's merge or tag history. In one case the stable Extended build available would have been a downgrade and lacked a feature that existed only on the development branch. Wait for a stable release aligned with the installed base unless the operator accepts development-build risk.
- Optional release monitoring, only when requested: follow `printer-control-and-safety.md` section 7; no watcher is implemented or enabled by this reference.

## 3. Live filament-runout (Auto-Refill) recovery: the scoped paused-job exception

Use when a running U1 pauses for filament runout instead of switching to a loaded standby toolhead. Investigation during an active or paused print stays read-only until the operator explicitly authorises a resume or remap.

Read-only diagnosis:
1. Identify the printer (section 1). Query live state: `print_stats`, `pause_resume`, `virtual_sdcard`, `toolhead`, `print_task_config`, `filament_detect`, the four `filament_motion_sensor eN_filament` objects, `gcode_macro INNER_RESUME` and all four extruders.
2. Confirm the failed physical tool by zero-based mapping.
3. Read the live Klipper log through Moonraker (log root listing, then the active Klipper log). Around the message `try to auto replenish filament` compare feeder or sensor detection, `backup info` (metadata at runout) and the current `filament info` and `replenish_ignore_color`.
4. **Matching pitfall:** different-colour refill allows ignoring colour only. Vendor, type and subtype mismatches can still reject a detected backup (a verified failure: standby `Generic/PLA` versus depleted `Snapmaker/PLA/SnapSpeed` logged `cannot auto replenish filament`). For planned remainder-spool chaining make the metadata compatible deliberately before the print; never falsify metadata during an active job.

Is manual remap safe?
1. Download the exact active G-code (`virtual_sdcard.file_path`) and read the unexecuted suffix from `virtual_sdcard.file_position`.
2. Enumerate future standalone `T0` to `T3` commands and `print_task_config.extruder_map_table`. A single-colour file with no remaining tool commands is much safer than a multicolour file that will select the depleted logical tool again.
3. Check temperatures stored in `INNER_RESUME`.

Recovery command (a **live-print mutation**, not a diagnostic): on verified stock firmware 1.5.2 the live macro accepted `INNER_RESUME REPLENISH=1 REPLENISH_EXTRUDER=<zero-based physical index>`, which selects the requested tool, auto-feeds, checks its sensor, restores temperatures, primes, cuts and cleans, and resumes. Never send it merely because an old reference mentions it. Re-read the current printer's live macro body first (firmware changes semantics), require explicit authorisation naming the target toolhead, verify the target sensor reports filament present, verify the remaining G-code and tool-selection risk, and after sending re-query `print_stats`, `toolhead`, the sensor, temperatures and recent log lines to prove the intended tool is active and printing resumed without a new exception. If any gate is uncertain use the supported fallback: load replacement filament into the depleted original toolhead and resume from the touchscreen. Never substitute a plain `Tn`, a generic `RESUME` or an improvised extrusion sequence.

Report live facts first (paused layer and progress, depleted tool, detected standby tool, Auto-Refill settings, the exact metadata mismatch), separate read-only inspection from the proposed mutation, and ask for confirmation immediately before sending.

## 4. Visible pause before a physical toolchange

When a running U1 waits above the model before the physical switch, keep the investigation read-only and separate temperature waiting from mechanics.

1. Read server info, system info, `print_stats`, `virtual_sdcard.file_position`, `toolhead.extruder` and all extruder temperatures and targets. Download an HTTP range of the live G-code around `; CP TOOLCHANGE START`.
2. In the block before `T[next]` check, in turn: nonzero `G4 P/S` (explicit dwell), `M109 ... T[next]` (blocking wait for the parked next tool's temperature), `M400` (queue drain), `M104` standby or preheat, `TIMELAPSE_TAKE_FRAME` and camera macros, `G10 S1` (firmware toolchange retract, not proof of a pause). Count the pattern across all toolchanges.
3. In the GUI and Klipper logs separate two times: the target change of the next head to the message `// extruderX -> extruderY` (wait before mechanics) and that message to `[Y] activating_move:0` (mechanical park and pickup). If the target rises in the first phase and the switch starts only when it arrives, the cause is `M109`, not a random hang, dwell or mechanics.
4. Slicer versus firmware: compare `change_filament_gcode` in old and new G-code footers; compare the project preset with the profile at the exact slicer tag (not current `main`); compare current `printer.cfg` with a pre-update snapshot (identical config does not exclude vendor module changes); read the official changelog (no entry means the new pause cannot be called an intended feature). The strongest A/B is **identical G-code** on firmware before and after; changing slicer and firmware together does not separate causes.
5. Verified example: the stock U1 profile in OrcaSlicer 2.4.2 already contained `wait_for_extruder_temp = true`, `M109`, `M400`, then `T[next]`; the same template appeared in G-code generated before the firmware upgrade. Fourteen live toolchanges showed roughly 4–5 s waits for a 256 to 260 °C rise and roughly 10–11 s for 220 to 240 °C before about 4–5 s of mechanical switching; no `G4`. A source diff of the vendor modules between 1.5.1 and 1.5.2 did not confirm a change in `M109` semantics. Honest verdict: the mechanism is the stock `M109`; timing correlation with the update is real but cannot be attributed to firmware without an identical-G-code A/B.
6. Mitigation: do not modify the running print. Do not disable `M109` or `wait_for_extruder_temp` blindly (the next head may be picked up or pre-extruded too cold). Report a suspected regression to the vendor with firmware, the G-code block, timestamps of target-to-switch, temperatures and the fact that the template predated the update. Later A/B ideas: same G-code on old and new firmware; controlled standby or preheat of the next head; moving the head to a verified safe XY before the blocking wait. Reducing a large standby delta may shorten the wait but increases ooze and keeps parked nozzles hot; change one thing at a time on a short test model.

## 5. Adaptive bed mesh (Extended firmware)

1. Idle check. Inspect a freshly sliced representative G-code: it must contain `EXCLUDE_OBJECT_DEFINE` commands (their polygons feed Klipper adaptive meshing). Inspect every `BED_MESH_CALIBRATE`: Snapmaker Orca may already compute adaptive boundaries and probe counts via its own placeholders and deliberately emit `ADAPTIVE=0 ADAPTIVE_MARGIN=0` to stop Klipper applying a second algorithm. Preserve that when the profile shows Orca owns the adaptation; only flip to `ADAPTIVE=1` after establishing the active profile supplies no bounded mesh of its own, keeping the vendor bounds, probe count, algorithm and margin.
2. With the printer idle, select the firmware's force-adaptive option (or its supported API setting), wait for the Klipper restart and require `klippy_state=ready`. A settings read-back alone is insufficient.
3. Do not enable Moonraker Object Processing when slicer labels already exist; it is a fallback that can delay large uploads.
4. Physical smoke test only after explicit motion authorisation, a current clear-bed check and a fresh standby confirmation: home, define a small synthetic object with `EXCLUDE_OBJECT_DEFINE` in a clear area, run `BED_MESH_CALIBRATE ADAPTIVE=1` with a small margin, append a `RESPOND` completion marker, poll Moonraker instead of trusting HTTP timing, and require an adaptive runtime profile, `probe_state=completed`, and `mesh_min`/`mesh_max` matching the synthetic polygon plus margin (a reduced probe matrix is evidence of adaptivity; successful homing is not). After the test lift and park and require ready.
5. A completed print's object list is transient; verify definitions in newly emitted G-code. Explicit `ADAPTIVE=1` in the slicer is preserved by the force wrapper and an explicit `ADAPTIVE=0` stays non-adaptive.

## 6. Timelapse corruption (green flashes, torn frames)

No-motion diagnostics only (GET and downloads); do not home, calibrate, print, change parking macros, reboot or flash as part of camera diagnosis. Isolate the capture boundary: list file roots, download the original MP4 from the timelapse root (mobile sharing may re-encode; compare original and upload with ffprobe); run `ffmpeg -v error -hwaccel none -i VIDEO -f null -` and record its own exit status (a clean decode proves decodability, not correct pixels); inspect individual frames, not only contact sheets (every-fourth-frame sampling can miss most damaged frames; a downscaled stream with a green-dominance count can shortlist candidates); read only the camera section of the firmware settings. For the community camera provider, the upstream issue #736 and pull request #806 of the Extended firmware describe NV12 frames read at YUYV size in the raw-camera bridge. Matching version, provider and symptoms give a strong hypothesis, not proof. Verify a proposed release contains the merge commit `15c081380a9302617b40bb6e01a307d5945eb1f2` for pull request #806 (or explicitly resolve and record the full merge SHA first) through the repository compare API, before the release-ancestry comparison (a merged pull request or a newer number is insufficient; distinguish rolling from curated builds). Never flash experimental firmware for a camera-only issue. A provider change is a separate mutation; a new timelapse through the affected recording path is the repair gate; live JPEG or RTSP cannot certify it; existing damaged frames are not restored by an upgrade; deleting or interpolating frames is a lossy salvage sibling. Report diagnosis, applied changes, occupied-bed blockers and verified acceptance separately.
