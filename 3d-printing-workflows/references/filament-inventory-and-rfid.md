# Filament inventory (Spoolman) and RFID tags (OpenRFID, OpenSpool)

Optional. Spoolman, OpenRFID/OpenSpool and Snapmaker U1 Extended firmware are version-dependent; read the live service and the matching documentation first. Use `<spoolman-host>` and `<printer-host>` placeholders; never put real addresses, tokens or order data in a skill or report. Printer-side safety rules are in `printer-control-and-safety.md`.

## 1. Adding purchased spools to Spoolman

1. Inspect the live service first: info, OpenAPI, vendor, filament and spool endpoints. Do not guess payloads.
2. Read existing vendors and filament definitions before adding anything. Match by vendor, filament name, EAN or article number. If the filament type exists, patch its metadata or price instead of creating a duplicate; then create physical spool rows.
3. Before a multi-row import trigger the service's database backup if available. Make the import idempotent: put a deterministic marker in each physical spool's `comment` (order reference, EAN or SKU, `item N/quantity`), re-query current spools and skip only exact already-imported rows, so a partial run is safely resumable without suppressing legitimate repeat purchases.
4. Create one spool row per physical purchased spool or refill, with price per unit (line total divided by quantity) on the spool and, if useful, the filament definition; `initial_weight` and `remaining_weight` (for example 1000.0 for a full 1 kg refill); the listed core or tare weight as `spool_weight`; and a location. Use product pages or authoritative metadata for EAN or SKU, temperatures, material, density, tare and colours.
5. Verify from a fresh read: exactly the purchased count for the order exists, and every created spool ID has the right filament link, price, weights, tare, location and comment. A successful POST is not completion.
6. **`extra` fields:** Spoolman (0.23 observed) validates `extra`; arbitrary keys can be rejected with "Unknown extra field", and values must be JSON-encoded strings (a plain URL string can fail). Use existing known keys (for example `url`, sent as a JSON-encoded string) and put EAN, SKU and order notes in `comment` unless extra-field definitions were inspected or configured. Let the supported SpoolLink component create and manage its own `card_uids` and filament `variant`; do not hand-write double-serialised values except to diagnose it.
7. Multi-colour filaments use the `multi_color_hexes` and `multi_color_direction` fields rather than a single colour. Transparent colours may use a hex with alpha; choose a visually useful approximation.
8. For spool-by-spool physical identity, keep one row and one tag UID per physical spool or refill even for identical material and colour; print the inventory ID on a physical label to reconcile duplicate-looking spools.

## 2. Stock versus Extended firmware, tags and the data model

- Stock U1 firmware reads the vendor's proprietary signed MIFARE Classic 1K tags; user-written NTAG/OpenSpool tags are not supported by stock firmware. Extended firmware (a complete custom firmware, not an installer layered on stock) adds OpenRFID and OpenSpool records on NTAG215/216. OpenSpool tags can be prepared on stock firmware; they will simply not be recognised until Extended is installed, and third-party filament can be selected manually as generic material and colour meanwhile. Distinguish starting a print with third-party filament (works manually on stock) from enabling RFID automation, and wait for a stable aligned-base release when automation can tolerate the delay.
- **Live read-only capability check** before recommending installation or edits: server info (look for `spoolman` and `spoollink` in loaded components), server config (`[spoolman]`), system info (machine type, installed firmware). If neither components nor config list them, a browser UI cannot simply be pointed at Spoolman; a supported firmware or component path is needed. Never restart Klipper, Moonraker or the printer during a print to investigate.
- **Tags:** prefer rewritable adhesive **NTAG215** (13.56 MHz, NDEF, ISO 14443-A, roughly 25–30 mm; about 504 usable bytes). NTAG216 works but adds nothing. Avoid NTAG213 (too small) and ISO15693 or OpenPrintTag tags (the reader path does not support them). Use anti-metal tags only when mounting on metal. Keep tags rewritable while establishing the workflow. Minimum OpenSpool fields: `protocol`, `version`, `type`, `color_hex`; useful optional fields include `brand`, `subtype`, temperature ranges, `weight`, `diameter`, transparency and additional colours.
- **Writing:** Android with Spoolman: use a writer that binds the tag UID to the exact existing spool (for example SpoolPainter): configure the live Spoolman URL, choose the spool, then Write (Save and Write are separate actions; form completion is not tag pairing), then read the Spoolman row back to confirm the UID in `extra.card_uids` before loading the spool. A Web-NFC writer (Chrome) writes OpenSpool metadata but does not by itself create inventory identity binding. iPhone: generate the OpenSpool JSON and write exactly **one NDEF MIME record of type `application/json`** with a generic NFC tool; plain-text and URL records are not equivalent. With any writer verify a single `application/json` record and read the tag back before use.
- **Data model:** OpenSpool carries material, colour and temperature metadata; SpoolLink resolves the immutable tag UID to one physical Spoolman spool through the `card_uids` custom field, applies metadata to the lane, switches the active spool on tool changes and attributes consumption to the right spool. A UID is moved away from any previously associated spool. An optional embedded spool ID on the tag is not the inventory authority; UID-to-row binding is. `SET_SPOOL_ID LANE=E0 SPOOL_ID=<id>` is a supported printer-side fallback after the tag has been scanned in that lane, not the default pairing path.
- **Placement:** direct-on-spool: hold or tape the tag on the spool cheek facing the printer's reader coil (expected distance about 1–3 cm), and position it temporarily before permanent adhesion. External dry box: do not prescribe adhesion to the spool cheek; keep the tag in the dedicated token or holder paired with that spool or box, dock it at the adapter for the selected channel, and test the complete token, dock, lane scan chain. Existing vendor tags can interfere; do not stack active tags.
- **Vendor and profile compatibility:** the slicer may hide an unrecognised vendor and profile combination. Use OpenRFID's force-generic-vendor mode when compatibility matters, keep the real vendor and exact product identity in Spoolman, and map local variants to recognised slicer profiles deliberately.
- **Consumption accounting during a print:** verify the physical-tool mapping from the logged `MAP_TABLE` (see `snapmaker-u1-operations.md` section 1), confirm the active SpoolLink `spool_id`, then compare Spoolman `remaining_weight` and `used_weight` across reads. A small `pending_reports` quantity is normal batching, not an accounting failure.

## 3. OpenRFID scan-state gates

- `filament_detect.info` is the result of the most recent scan, not a live presence sensor. In the U1 Extended base configuration `auto_read_mode = false`: the reader loop does nothing while every channel state is `0`. A request such as `FILAMENT_DT_UPDATE CHANNEL=<0..3>` sets one channel's state to `1`; OpenRFID observes it through Moonraker and scans that lane (20 attempts every 0.2 s in the observed configuration). A successful scan writes the cached tag record; an exhausted no-tag scan emits `tag_not_present` and clears it. A quiet `openrfid.log` therefore proves only that no scan was requested.
- Channel naming gate: `0` is E1 and `3` is E4. For a real scan proof combine the channel-indexed tag metadata and UID with the matching `filament_motion_sensor` showing `filament_detected: true`, then match the normalised hexadecimal UID to Spoolman's `extra.card_uids` before claiming physical spool identity.
- Run a manual scan only when idle and explicitly authorised, with exactly one controlled request for the named lane; it can update or clear that lane's cached metadata and fan out to SpoolLink, so it is not a harmless refresh during a print. Tail the OpenRFID log, then re-read `filament_detect` and Spoolman. If the command is in Moonraker's G-code store but the log repeatedly reports reader wake-up or scan errors before any UID, the request path works and the fault is below tag parsing and Spoolman: compare the adjacent slot that shares the reader IC but selects a different coil before changing tag metadata or bindings.
- Do not enable continuous `auto_read_mode` merely to obtain removal detection; inspect the pinned runtime first, because its absence-event behaviour and polling load must be proven for that version.
- Enabling Spoolman on the printer: change settings only after proving a non-printing state; enable Spoolman with the verified LAN URL and force-generic option if third-party vendors need it; enable OpenRFID separately; after each restart require `klippy_state=ready`, `spoolman` and `spoollink` in server info, a matching `[spoolman]` block in server config, and the Spoolman status endpoint reporting connected. The RFID workflow is complete only after a physical tag scan and a UID-to-Spoolman binding succeed.
