# Slicer forks, build hosts and Linux runtime

Versions, issue numbers and numbers below are examples from specific sessions; re-verify them.

## 1. Moving a calibrated profile into a slicer fork

Do not clone the whole preset tree or declare success because JSON files parse and inheritance resolves.

- Before editing any profile, close the fork and make a recoverable copy or archive of its user filament directory and its app config, and keep the restore path (a local recoverable copy; no fixed private account path and no off-workstation archive is required).
- Keep the fork's vendor machine and toolchange code, mixed-filament definitions and colour-specific material settings as the parent. Add minimal user overlays only for physically validated settings (Z-hop, retraction, seam behaviour, tower brim, calibrated flow ratio and pressure advance).
- Take only the source filament's explicit calibration overrides; do not bulk-copy a resolved profile. Give each overlay a descriptive new name, a valid four-part `version` (for example `2.3.5.0`; otherwise the loader can silently skip the file), `from: "User"`, a parent that is **proven to resolve in the running fork** (a parent visible in the system JSON directory may not be in the loaded collection), `compatible_printers` naming the actual custom machine, and a unique `filament_settings_id`. Keep fork-specific colour-mixing parents for colour work; use general parents for single-colour materials.
- Acceptance is an end-to-end UI gate after a **cold restart**: the custom names appear in their dropdowns, the process stays selectable with the custom machine, the chosen pair survives restart, and the log shows each custom profile loaded with the expected count. File existence, schema validity, direct config edits and a successful launch are not evidence that the slicer registered presets. If the gate fails report it unresolved and inspect the fork's actual preset-discovery convention (in one fork the selected process persisted inside the preset row of the selected machine) instead of implying a remedy.
- In vendor forks the left **Printer card** selects the connected physical device and may list only vendor system devices; validate a custom machine in the Printer settings selector and the process in the Process selector. Cross-check that the active nozzle on the card matches the intended profile nozzle (a visible 0.2 mm device state with a 0.4 mm process is a mismatch).
- When comparing two slicers or forks, resolve machine, filament and process through every `inherits` parent and compare **effective bundles**, not display names. Profile directories can use account GUID folders instead of `default`; exclude archival `*_old.json` files that share an internal name with the active profile (a naive name-to-file map will overwrite it and produce a false configuration). Compare seam-critical settings in this order: `wall_generator` (Arachne versus Classic is high signal), retraction and wipe cluster, seam gap and position, staggered seams and wall order, flow ratio, PA and temperature, max volumetric speed and actual outer-wall speed (a lower cap can make a competitor look more stable), then unrelated differences. Safe A/B: change one cluster in a named sibling profile, slice the same project, compare G-code and the physical seam. Keep deliberate anti-scrape Z-hop unchanged unless G-code proves involvement; do not start with global flow, a positive restart extra or scarf seam. Upstream issues are leads, not proof; a useful report needs the exact project plus matched verbose G-code from both slicers and a one-variable reproduction.
- Evidence gate for any profile comparison: distinguish a saved custom profile, a genuine system bundle and transient UI edits, and never assert that a remembered UI setting persisted until the active JSON proves it.
- `seam_gap` is a physical planned loop-end gap: a positive gap alone cannot explain a seam that is more closed than an otherwise matched 0 % profile. Confirm which was the active process and inspect the emitted G-code; keep the one-cluster A/B causal.

## 2. Development host versus validation host

When developing a slicer fork separate the **development host** from the **physical validation host**. A user's desktop may hold the active profiles and be ideal for final preview, slicing and printer tests but can be restarted or powered down, so it should not be the default long-running build box. Use a stable automation or server host for the canonical checkout, branches, builds, unit tests, instrumentation and artifacts. Treat the workstation as an integration target: install a separately named experimental build without replacing the stable slicer, import or read its profiles, then do visual toolpath checks and physical A/B prints. The install stage must be non-destructive with a rollback path.

On the development host build the unmodified fork first and run the full `ctest` suite before edits; test executables alone are not a green baseline.

## 3. Resource containment for builds

- Do not start a heavy build on the user's workstation or on a shared service host without approval and a resource plan. Slicer dependency and C++ builds can saturate CPU and RAM and make a desktop, WSL or SSH unresponsive. Constrain builds explicitly (for example `nice -n 10 ./build_linux.sh -j 4 ...`; unbounded parallelism is not an acceptable default).
- If the workstation lags, user responsiveness wins: stop the tracked build first and verify recovery. A WSL or VM shutdown kills unrelated processes, so use it only with explicit approval after the ordinary stop fails.
- On a shared server or NAS treat a slicer C++ build as a memory-risk workload even when CPU is constrained: several concurrent `cc1plus` processes can exhaust RAM and swap, and the kernel may kill unrelated services before the build fails. Diagnose an incident from the previous boot's journal before assuming disk or RAID trouble: boot IDs, `Out of memory`, `Killed process`, `Free swap = 0`, `cc1plus` and the largest resident processes, then current RAM, swap, disk, container and service health.
- Prefer the upstream container runner (`build_linux.sh -g`) but do not mistake a container for containment: add hard limits (`--cpus`, `--memory`, `--memory-swap`, `--pids-limit`) **and** the matching `-j N` and `CMAKE_BUILD_PARALLEL_LEVEL`. A conservative starting envelope for a 32 GiB server that also runs services was 2 CPUs, 8 GiB memory, 8 GiB memory plus swap (no host-swap borrowing) and 512 PIDs. Verify the wrapper's dry run emits those exact flags and run a bounded `docker run ... /bin/true` smoke test. A dry run proves argument construction only, not a completed compile.
- Before removing build tooling simulate it (`apt-get -s purge ...`) and read the whole removal set. On hosts with GPU kernel-module rebuilds, GNU build packages can be dependencies of the driver; removing them can cause an outage. A narrower cleanup is the slicer front-end tools (for example `cmake`, `ninja-build`, optional `clang`) without `autoremove`. Read back `command -v` for removed tools and the package state of the driver and compilers, then check affected services.
- Agent gateways: a child process may live inside the gateway's service cgroup; with an out-of-memory policy that stops the unit, one runaway test can stop the whole gateway. Run adversarial tests under an explicit ceiling, and know what each one bounds. `ulimit -v` (RLIMIT_AS) limits the virtual address space of one process, inherited per process; it is not aggregate process-tree RAM plus swap and not cgroup containment. For aggregate adversarial work use an operator-approved separate container or cgroup scope with memory (`memory.max`), swap (`memory.swap.max`), PID and CPU limits, and verify that the limits actually took effect; a test run inside the gateway's own cgroup is not isolated, and no isolation scope guarantees zero host risk, so keep the hard out-of-memory and pressure stops. This is a clarification only: no scope, container or service is created by this reference. Primary references: Linux `getrlimit(2)` (https://man7.org/linux/man-pages/man2/getrlimit.2.html) and the kernel cgroup v2 guide (https://docs.kernel.org/admin-guide/cgroup-v2.html).

## 4. Linux runtime troubleshooting (sluggish, black canvas, missed input)

Isolate the failing boundary before touching printer profiles.

1. Verify the installed package matches host architecture. An ARM build on x86_64 runs under emulation and makes 3D interaction unusably slow. Replace only the application with the official matching asset (selected from the vendor's release API, not a guessed remote) and verify the package reference and ELF architecture; preserve configuration.
2. If the UI chrome loads but the Prepare canvas is solid black, inspect the running process, library mappings (GL, EGL, vendor driver) and the user journal before resetting settings. Loaded vendor EGL libraries mean this is not automatically a missing-driver problem. A vendor release can have a known renderer defect on a driver and display-server combination even with the correct runtime installed; check current upstream issues and releases.
3. Never reset the user's profile or configuration as a first-line fix; it is destructive and unsupported by evidence. If an immediate slicer is needed, standard upstream OrcaSlicer may be a temporary fallback after checking it meets the user's printer workflow; a separately installed, clearly labelled experimental build from an upstream fix branch needs explicit approval and is not an official fix.
4. For missed clicks or shortcuts define the exact failing sequence and preserve the failed state (random clicking can restore focus and destroy the reproduction). Check independently: raw input event (evdev or libinput), compositor and toolkit focus delivery, GUI-thread saturation and repetitive log loops, and the application's command-state handling. Raw event absent means device, kernel or libinput; present but command absent means focus, toolkit or application; high main-thread load with repeating GUI log activity means possible delayed event-loop handling, not proven hardware loss. One known focus-shaped lead is an object visibly selected through the object list that ignores shortcuts until clicked on the canvas (upstream issue OrcaSlicer/OrcaSlicer#10268); test it as a hypothesis by comparing selection routes.
5. Do not infer free-spin scrolling from several layers per wheel step: compare raw `REL_WHEEL` and `REL_WHEEL_HI_RES` or libinput output for one deliberate detent and another application.
6. Package migration (Snap or Flatpak to AppImage) is an isolation experiment, not root-cause proof. Back up sandbox and native profiles, verify the upstream digest, launch inside the real graphical session and prove the native config path is active, keep a rollback until the exact symptom passes, and report confinement denials and crashes as separate findings.
7. Reporting discipline: say "the replacement build is healthy" only for startup and runtime evidence, and "the input bug is fixed" only after the user repeats the original failing sequence successfully. If the symptom persists, retract the causal hypothesis and continue from the live failed state.
