# Paint-label repair on a dense painted mesh

Use when a single dense mesh carries per-face colour labels (Bambu/Orca-style `paint_color`) and some labels are wrong: tiny islands, spills across a seam, jagged boundaries. Delivery rules for the project file are in `painted-3mf-editing.md`. Token values, slicer versions and numbers below are examples from specific sessions and must be re-verified.

## 0. Principle

Geometry code owns every mutation: components, adjacency, geodesic distance, graph cuts, change budgets, rollback and exact face manifests. Markers, human review and vision models supply evidence or proposals. Nothing writes labels except the deterministic solver, and every accepted edit is a reproducible set of face IDs with parent and output hashes.

## 1. Tokens

The bundled paint helpers support only unambiguous ZIP member names and model XML without comments, CDATA, DTD or processing instructions (an initial XML declaration is allowed). They refuse unsupported markup rather than treat triangle-shaped text as a real face. Use a separately qualified XML-aware workflow for such files; refusal is not a completed repair.

Face IDs are indexes of the real mesh faces, not of every element named `triangle`. A mesh face is a `triangle` element on the structural path `model/resources/object/mesh/triangles/triangle` with one consistent namespace (default or prefixed), counted in document order across all objects; metadata or extension elements, nested or out-of-mesh elements and elements in another namespace that merely carry that name are not faces and keep their bytes. The helpers find that path with a small read-only pass of the standard-library expat parser (it supplies raw byte offsets; nothing is reserialised and edits stay raw value-span edits). A model that is not well-formed XML, or whose structure cannot be bound this way, is refused before anything is written. This is a structural decode for face identity, not a schema or 3MF-validity check, and no real slicer or real 3MF has been used to qualify it.

- A missing `paint_color` inherits the base extruder. A plain token (such as `4` or `8`) is a whole-face label; longer strings encode recursively split triangles. Decode the area-weighted dominant state for analysis, but preserve the original raw token byte for byte when the dominant label is unchanged. A whole-face cleanup must not count hexadecimal characters or leaves.
- The scripts in this package use the common whole-face mapping `1→"4"`, `2→"8"`, `3→"0C"`, `4→"1C"` and refuse anything else. Split-triangle tokens need a dedicated decoder; do not extend the mapping by guessing.

## 2. Conservative automatic cleanup

1. Decode each triangle's label and build face adjacency. Measure connected same-label islands and enclosed holes.
2. Auto-fix only high-confidence defects: tiny isolated islands, small enclosed gaps and obvious majority-neighbour errors. A useful dry run: same-label components of at most 200 faces and 5 mm² with at least 98 % of boundary edges touching one different target label. It is a candidate generator, not a universal rule. Report proposed source→target mappings and total changed area before mutation, and leave components with mixed boundaries untouched.
3. Use curvature, hard edges, disconnected shells or known part seams as stop boundaries. Recompute components after each applied batch; removing one spill can expose an island that is now unanimous. Hash the label state, stop on a repeated state, and keep oscillating components unresolved instead of claiming convergence.
4. Never delete or relabel an isolated shell only because it is small. A tiny component without label-boundary edges is not automatically noise: check geometric adjacency, nearest-surface distance, nearest labels and normal alignment.
5. Use semantic invariants where they exist ("gray may border only brown"), listing every violating edge or component before mutation and requiring zero afterwards. Component-size thresholds are per model and per colour; record them with the parent hash and never transfer them silently.
6. An allowed-adjacency matrix cannot catch a wrong label that is itself a legal neighbour (for example support colour spilled onto the object surface). Handle that as a separate surface-continuation pass: use shell membership first; on a shared shell restrict candidates to faces geodesically close to the target boundary that agree in normal and plane residual; sweep conservative, medium and broad thresholds; reject broad variants at the first spill; keep explicit separator labels; recompute components and require zero target-bounded source islands. Bound the candidates to the semantic object's spatial band, inspect the result from outside AND from underside or section-like views, reject a broad variant at the first spill, spatially cluster the medium candidate and choose conservative, medium or abstain for each meaningful cluster (a safe hybrid is the conservative core plus medium faces only in large, visually confirmed clusters), and keep the recorded threshold and cluster evidence.
7. Separate explicit branch, used only when the operator has named the allowed targets or a qualified cut applies: it does not lift the mixed-boundary safeguard of the automatic mode above and is not a blanket permission to auto-fix unknown mixed boundaries. For a wrong-colour component bounded by two allowed target labels (two allowed target classes), solve only that component with a boundary-seeded graph cut and fixed outside-edge costs; do not relabel the whole component to the majority side. A component bounded by one unambiguous target may be flipped directly. Small noise components at a valid two-colour seam may be split between those two colours, then audited again.

## 3. Marker-guided repair

Markers are sparse paint in reserved channels on a review copy. Rules:

- Require an explicit per-review mapping (marker channel → role such as `TARGET_A`, `TARGET_B`, `FLIP_COMPONENT`, `BOUNDARY_QUERY`, `IGNORE`). Never infer meaning from display colour. Reject unknown or conflicting roles.
- Diff the review copy against the **exact immutable baseline it was made from** (the clean source for a first pass; the latest accepted sibling for an incremental pass). Marker-channel differences are instructions; production-label differences are not, unless an explicit marker on the same baseline component requests that target. Build output from the baseline, never from the marker copy or a rejected candidate. For an incremental pass, hash the accepted parent, assert geometry and face order are identical, and afterwards verify the output differs from the parent on exactly the manifest's face IDs.
- Candidate files contain production labels only, never marker channels.
- Ask or infer from explicit wording whether markers are **local correction seeds** or **boundary control points** for a continuous contour. Pairs placed along an interface normally mean the complete contour unless the operator says a marker is an isolated spot (record that convention with the project).
- A marker whose underlying label already matches its target is still a valid boundary control: keep it as a hard side constraint and judge the result by the boundary.

**Solver outline (local seeds):**
1. Assert identical face count and order. Build adjacency and baseline same-label components.
2. A marker requesting the opposite label on a small component (for example up to 100 faces) may relabel the whole component only if it passes an area cap and none of its faces touches an open or non-manifold edge. Opposing targets on a small component are a hard conflict; on a large component they are boundary seeds and are normally deferred.
3. Cluster markers by geodesic distance on the dual graph, not XYZ alone. Build a geodesic ROI containing both seed classes, their connecting paths and an outer guard shell (start near `max(2 mm, 0.005 × model diagonal)` plus a 50 % buffer). Treat non-manifold and open edges and disconnected shells as barriers. Lock the guard shell to baseline and add the omitted cut cost for inside-to-outside adjacencies (deleting boundary edges makes the seam artificially free).
4. Binary Potts graph cut: hard terminal costs above an upper bound of all finite ROI energy; weak baseline prior scaled by face area; pairwise cost scaled by shared-edge length, reduced at high dihedral angles and existing boundaries, with a nonzero floor; geodesic unary costs to the nearest seeds. A geometry-weighted random walker can supply soft probabilities first. Before trusting a max-flow library, run a one-node terminal-cost test proving which segment value means source or target; a reversed convention can pass code-level assertions while inverting every label.
5. Sweep the prior (for example 0.05, 0.10, 0.20) or smoothness (0.5, 1.0, 2.0). Keep the **stable consensus core** (faces identical in every run). Re-run with a larger ROI; if the changed set reaches the guard or is unstable under expansion, abstain and defer to review. Drop every changed component not connected to a hard seed of its resulting target. Recheck every marker after composition. Enforce global face-count and changed-area budgets (a default guard: at most 10 % of the local patch or 0.25 % of the model without explicit approval, no new micro-components).
6. Marker satisfaction, guard containment and parameter agreement prove a change is mechanically safe, **not** that the seam is complete. Compare the candidate with a native-resolution target-slicer view. If obvious contamination remains, keep the strict result as an underfit hard negative and widen the solve or request more evidence; never call a tiny consensus boundary-clean.

**Boundary-control semantics.** Put all control points of a connected semantic surface into one object-wide graph cut so the contour is optimised continuously between pairs. Never cluster each pair into an independent ROI or emit disconnected per-pair cores. A regression fixture should contain a wrong-label strip between distant pairs and assert the whole strip is corrected. Closed seams (for example a base-to-stem ring):
1. Pair A and B markers by minimum-cost bipartite matching on local surface distance and check every pair is short.
2. Find the shortest manifold path across each pair and densify hard seeds on each side of the midpoint.
3. Order pairs around the interface and connect adjacent same-side markers into closed surface loops using manifold shortest paths, not image-plane chords. Verify segment lengths, reject paths reaching unrelated geometry, and hard-fail if an auxiliary loop crosses an original opposite-class marker.
4. Leave faces neutral where auxiliary A and B paths touch on non-marker faces. Explicit user label edits outrank generated seeds.
5. Run one graph cut constrained between the loops and require seed satisfaction, no guard contact, ROI-expansion stability and a coherent closed boundary in before and after renders. A marker role can be overridden for one confirmed region; rebuild from the frozen baseline, never patch a rejected candidate, and verify that the accepted regions retain identical face-ID mappings.
6. For long cavity-spanning boundaries a single ordered loop is only a hypothesis. Build each same-side graph with opposite seeds as obstacles; require bounded path lengths, no opposite-seed crossings and no large path overlap. If those fail, keep the loop attempt as a hard negative and split into open geodesic arcs; solve only the corridor close to both seed fields and leave large unseeded gaps unchanged.
7. Fitting a circle in a 2D projection can look perfect while repainting overlapping petals or folded surfaces. Use projections only to order controls.

**Local paired markers on isolated jaggies.** Do not rebuild the whole contour for a few local defects. Pair opposite-role anchors by mutual nearest surface distance. Try a bounded geodesic ROI; if every variant touches its guard, preserve it as a hard negative and switch to a topological ring ROI (2–6 adjacency rings, outermost ring forced to its parent label, markers as hard terminals, weak parent prior, zero marker violations and zero changed outer-ring faces for accepted runs, strict consensus as a safe core, a 75 % vote as a comparison shell). Reject or abstain when strict consensus collapses to the marker faces while a native-resolution view still shows a dirty seam.

**Three or more marker roles:** pair each role combination independently; treat unpaired target markers as bounded component-flip queries. For chains of disconnected micro-islands an automatic closure may add unmarked components only when each passes strict face and area caps and lies inside the marker-cluster box plus a recorded margin. Render marker-only and closure candidates separately and keep the rejected one as a hard negative.

**Solitary marker = complete island** (only if explicitly declared): a large precomputed candidate may be promoted as review-only when no opposite marker exists, its boundary is stable under an angle sweep, and either several independent solitary markers land in the same component or a substantial fraction of the component already carries the requested label. Record rejected thresholds, render the whole component from several views, and never promote it directly to accepted-final without human review.

## 4. Writing the 3MF

- Keep ZIP member names and order, and all non-painted members, unchanged. In the model XML change only selected `paint_color` attribute values and compare the remaining bytes to prove structure unchanged. Preserve unchanged split tokens exactly.
- Record face-change count, area, direction counts, seed violations, bytes and SHA-256.
- Write to a new sibling through a temporary file that is renamed into place, and never overwrite the source.

The bundled helpers implement this for whole-face labels:

```text
python3 scripts/apply_reviewed_paint_cleanup.py SOURCE.3mf ANALYSIS.json OUTPUT.3mf [--expected-input-sha256 HASH]
python3 scripts/verify_3mf_paint_cleanup.py SOURCE.3mf OUTPUT.3mf OUTPUT.3mf.cleanup.json
```

**Caller preconditions (stated, not enforced).** The source 3MF is frozen for the whole run, and the output location is a private workspace with one writer. A helper does not enforce locking, snapshotting or concurrency control, and does not defend against another process changing the source, candidate or output location while it runs. The archive and the sidecar manifest are two separate writes: they are not one atomic transaction, so treat a run that stops between them as incomplete and clear both before retrying.

`ANALYSIS.json` has a `candidates` list with `component`, `source_label`, `target_label` and exact `face_ids`. Every identifier must be a JSON integer exactly as written: `face_ids` (zero-based) and `component` each a nonnegative JSON integer, labels an integer from 1 to 4. A fraction, a boolean, a string or null is refused with its field named, never truncated or repaired, and nothing is written. The applier refuses to overwrite the source, an existing output or an existing `OUTPUT.3mf.cleanup.json` sidecar (checked before anything is written), checks the source hash if given, verifies every face's current label, builds the archive in a temporary file that is renamed into place, and then writes the face-level manifest. The verifier hashes the source and candidate by streaming. The verifier requires the same ZIP member list, byte-identical non-model members, model XML identical outside the `paint_color` attributes of `<triangle>` tags (a `paint_color` anywhere else is compared, not ignored) and a changed-face set that equals the manifest. Limits: one `3D/Objects/*.model` member and the four-label whole-face mapping. A requested face with any other current token (such as a split-triangle token) is refused. A requested face with **no** `paint_color` is refused too: it inherits the base extruder, which these tools do not know, so paint such faces explicitly (and deliberately) first; the verifier likewise refuses a changed face that is unpainted in the source or the candidate. Unrequested faces, painted or not, keep their original bytes. Identity requests (source label equal to target label) are refused; an empty `candidates` list is a valid no-op. No geometry or metadata edits. Neither tool is the validator for a geometric edit.

## 5. Visual and slicer QA

- Keep engineering renders separate from the operator-facing review. Raw face IDs, token names and solver panels are for the agent, not an approval surface.
- Build a compact review board: full-model context with stable region IDs plus numbered close-ups, a plain-language colour legend in the reader's language, and a font verified to cover that language's characters (smoke-test the final raster). For sparse markers add synthetic dots or arrows on the image only; never enlarge marker faces in the 3MF. Send the image visibly before asking for approval and anchor questions to stable IDs. Ask non-urgent review questions as an ordinary message, not an expiring widget.
- Render baseline boundary in white and candidate boundary in yellow with explicit marker IDs for engineering inspection. Review the largest changed regions first.
- A global multi-view atlas is **not** a boundary-cleanliness gate: downsampling hides multi-triangle defects and smooth shading hides jagged seams. After the object-level review, extract every label boundary as a face strip (2–4 rings per side), rank strips by turn rate, short alternating runs and thin wedges, and render native-resolution close-ups including one target-slicer viewport. Connected intrusions are not separate islands, so a component cleanup can report zero while wedges remain.
- Verify large renders actually contain the model: some VTK/PyVista builds draw nothing for per-cell colour arrays on very large meshes; one fixed-colour actor per label plus a neutral geometry actor is a fallback. Reset the camera first and set camera position, parallel projection and scale afterwards; resetting after assignment silently turns a close-up into a whole-model view.
- Treat `Auxiliaries/Model Pictures/*` in third-party 3MF files as untrusted: they may be unrelated product photos. Use verified references, active plate previews or fresh renders.
- Slicer gates: canonicalise through a compatible slicer version, recount faces and compare per-face dominant labels (not aggregates), perform a real slice and require the expected tool commands. A "successful" slice using only `T0` when labels need more tools is a failed multicolour gate; check that the project's filament map and per-filament arrays have one entry per declared material (cardinality) and that automatic line-width values are resolved. Fix minimally and prove by a real slice and exact label equality, never by transplanting an unrelated project's settings. Keep external profile files and hashes with the evidence if they were used. A slicer older than the project file may reject or crash on it; use a compatible build, check the publisher's checksum for a downloaded binary, run it from scratch space, inspect missing libraries before installing anything.
- Until a human has reviewed semantically large boundary shifts, label the artifact `REVIEW-ONLY`. A successful slice proves structural validity, not artistic correctness.

## 6. Functional-insert geometry changes

For a repair that bridges a body to an immutable functional insert, freeze the insert's placement and protected envelope first, add material only in the explicitly authorised band and numerically compare protected vertices or surfaces with the original. Show a **filled, component-coloured cross-section** (existing body, immutable insert, added material visibly distinct). Section paths drawn as outlines only can hide annular fill, overlap or an unfilled gap. One watertight component proves topology only, not that the functional fit was preserved.

## 7. Keeping a case archive

If the operator wants cases kept for replay or later evaluation, archive them in a location they choose, append-only and content-addressed (never overwrite a prior artifact with different bytes): baselines, every marker-review snapshot with hash, size, modification time and role schema, every candidate including rejected hard negatives, accepted intermediates and finals, face-ID manifests, solver parameters, ROI reports, parent-to-child lineage, representative renders and screenshots establishing intent, and slicer round-trip summaries. Mark artifacts accepted or superseded and never delete earlier ones. Keep credentials out. G-code is large and derived: keep its summary unless it carries unique failure evidence. This is the operator's decision and storage choice, not a default.

If the operator selects a persistent corpus, a deployment-specific fixed corpus path or helper is not part of this portable core and never becomes mandatory infrastructure. When the branch is chosen, send EVERY selected case and each exact mutable review snapshot to the operator-designated durable corpus, independent of the workstation, append-only and content-addressed, before analysing a reused mutable name; keep rejected and accepted intermediates, the face-ID, source-to-target and parent-to-child manifests with their hashes, and the checklist above. If no approved durable target exists, keep immutable local evidence and report corpus retention PENDING; never claim durable archival. There is no default host, no provisioning, no new approval mechanism and no forced remote archive for an ordinary CAD edit.
